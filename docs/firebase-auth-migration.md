# ترحيل دخول الموظفات إلى Firebase Authentication

قبل النشر، يجب إنشاء **حساب Firebase Authentication باستخدام Email/Password لكل موظفة**، ثم إنشاء وثيقة وصول يدوياً من Firebase Console أو عبر إجراء إداري موثوق (Admin SDK):

- المسار: `staff_access/{uid}`، حيث `{uid}` هو Firebase UID للحساب.
- الحقول المطلوبة: `active: true`، و`staffId` الذي يربط الحساب بمعرّف سجل الموظفة (أو بريده الإلكتروني)، و`role` المطابق لدور سجلها في بيانات `users`.
- يجب أن يطابق بريد حساب Firebase بريد الموظفة المسجل. تعطيل الوثيقة (`active: false`) يمنع الدخول، وتغيير الصلاحية يتم إدارياً فقط.

فعّلي Email/Password في Firebase Authentication وانشري `firestore.rules` إلى **قاعدة البيانات المحددة في `firebase-applet-config.json`** قبل النشر؛ لا تفترضي أنها قاعدة `(default)` إذا كان للتطبيق `firestoreDatabaseId` مستقل. غياب الحساب يظهر كخطأ اعتماد؛ أما الحساب الموجود بلا وثيقة وصول فعالة أو بلا ربط صحيح بسجل الموظفة فيُرفض مع رسالة تشرح إجراء التهيئة المطلوب. لا تُدرج كلمات مرور أو مفاتيح خاصة أو أي أسرار في هذا الدليل أو المستودع.

قواعد Firestore تمنح الموظفات المفعّلات وصولاً للقراءة والكتابة إلى وثيقة الحالة المركزية المشتركة (`institution_database`). هذه الوثيقة مجمّعة ولا تفرض القواعد تقييداً على حقولها؛ لذلك فإن تقييد بياناتها بحسب الموظفة أو الدور يتطلب إعادة تصميم نموذج التخزين والقواعد لاحقاً.

## تنظيف بيانات الدخول القديمة قبل النشر

كانت نسخ سابقة من المستودع تتضمن رموز PIN تجريبية، كما قد توجد وثائق `staff_pins/{staffId}` في Firestore أو مفاتيح `ghaith_pin_*` على أجهزة مستخدمين قديمة. يعالج التطبيق المفاتيح المحلية ويمنع القواعد الجديدة قراءة/كتابة `staff_pins`، لكن **لا تنشري القواعد قبل حذف وثائق `staff_pins` القديمة إدارياً** من Firebase Console أو عبر Admin SDK؛ لا تسمح القواعد الجديدة للعميل بحذفها. اعتبري الرموز التي سبق نشرها مكشوفة، وأنشئي كلمات مرور Firebase Auth جديدة لكل موظفة، ثم اختبري الدخول بحسابات فعالة فقط.
